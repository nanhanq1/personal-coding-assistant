# 工业级加固标准

本文件定义模块加固的具体执行标准。AGENTS.md 中 P3 规则引用本文件。

## 核心理念

加固的唯一目标：**让当前模块达到可以放入生产环境的质量标准**。

不是"补几个字段"，不是"加一些检查"。一个模块只有同时满足 9 个维度的极致要求，才算"加固完成"。

## 节奏

- 每 2 周实现新模块后，安排 1 周专门加固
- 加固周不新增模块，只把已有模块做到极致
- 加固周结束时仍有维度未达标，继续加固，不进入新模块

## 九个极致维度

### D1：可观测性（出了问题能定位）

**达标标准：能根据 trace_id 完整还原一次工具调用的全链路**

必须实现：
- 每个核心操作必须有 trace_id，贯穿整个调用链
- 每个核心对象必须有唯一 id 和 timestamp
- 必须有结构化日志（JSON 格式，不是 print）
- 日志内容：时间戳、trace_id、操作名、输入摘要、输出摘要、耗时、状态
- 必须有调用统计：调用次数、成功率、失败率、平均耗时、P99 耗时
- 必须能根据 trace_id 查询完整链路

检查清单：
- [ ] 每个核心类有 `id` 字段（UUID）
- [ ] 每个核心类有 `created_at` 字段（ISO 8601 时间戳）
- [ ] 关键操作有 `trace_id` 透传
- [ ] 有 `ToolCallLogger` 或类似结构，记录每次工具调用
- [ ] 有统计接口：`get_stats()` 返回调用次数、成功率、耗时分布

### D2：健壮性（不会崩溃，能恢复）

**达标标准：注入任何坏输入，系统都能给出有意义的错误信息，不会崩溃**

必须实现：
- 所有输入必须有校验（类型、范围、格式、边界值）
- 所有失败路径必须有处理（不只是 happy path）
- 错误必须分级：可恢复 vs 不可恢复、用户错误 vs 系统错误
- 必须有重试策略（临时性失败）
- 必须有降级方案（依赖不可用时）
- 必须有超时机制（不能无限等待）

检查清单：
- [ ] 所有公开函数的参数都有类型和范围校验
- [ ] 所有可能失败的操作都有 try-except
- [ ] 错误信息包含：错误类型、错误原因、建议操作
- [ ] 有重试装饰器或重试机制
- [ ] 所有外部调用都有超时
- [ ] 有 `CircuitBreaker` 或类似降级机制

### D3：安全性（不会被滥用）

**达标标准：攻击者无法通过工具调用获取系统权限或泄漏敏感信息**

必须实现：
- 所有外部输入都视为不可信
- 所有输出都必须清洗（防泄漏、防注入）
- 必须有权限控制接口（即使当前只是 allow-all）
- 必须有审计日志（谁在什么时候做了什么）
- 敏感数据必须脱敏（密钥、token、密码）
- 必须有资源限制（文件大小、执行时间、内存）

检查清单：
- [ ] 所有输入都经过 `validate_input()` 校验
- [ ] 所有输出都经过 `sanitize_output()` 清洗
- [ ] 有 `PermissionChecker` 接口
- [ ] 有 `AuditLogger`，记录所有敏感操作
- [ ] 敏感数据有 `redact()` 函数
- [ ] 有资源限制配置：最大文件大小、最长执行时间

### D4：性能（不会成为瓶颈）

**达标标准：有性能测试报告，知道当前模块的性能上限在哪里**

必须实现：
- 必须有性能基准：正常情况下的耗时、内存占用
- 所有可能产生大量数据的边界必须有截断机制
- 必须有资源上限（最大文件大小、最大输出长度）
- 不能有内存泄漏（长时间运行后内存不会无限增长）

检查清单：
- [ ] 有 `benchmark` 测试，记录正常场景耗时
- [ ] 有 `stress_test`，记录极限场景表现
- [ ] 所有字符串输出有 `max_length` 截断
- [ ] 所有文件操作有 `max_size` 限制
- [ ] 内存占用在长时间运行后稳定（不会线性增长）

### D5：可测试性（能证明它是对的）

**达标标准：核心模块覆盖率 ≥ 90%，所有边界测试通过**

必须实现：
- 核心路径测试覆盖率 ≥ 90%
- 关键边界路径 100% 覆盖（超时、权限拒绝、网络失败、资源耗尽）
- 必须有集成测试（不只是单元测试）
- 必须有回归测试（修复 bug 后必须有测试防止再发生）
- 测试必须可重复运行（不依赖外部环境、时间、随机数）

检查清单：
- [ ] `pytest --cov` 显示核心模块 ≥ 90%
- [ ] 有 `tests/integration/` 目录，含集成测试
- [ ] 有 `tests/boundary/` 目录，含边界测试
- [ ] 所有测试可以 `pytest` 一次通过，无 flaky test
- [ ] 测试不依赖网络、文件系统、当前时间

### D6：接口清晰性（别人能用对）

**达标标准：新人看文档就能正确使用，不需要看源码**

必须实现：
- 所有公开接口必须有完整文档（参数、返回值、异常、示例）
- 接口必须稳定（不频繁变化，变化时有版本控制）
- 错误信息必须有意义（不是"error"，而是"参数 path 不能为空"）
- 必须有使用示例（正常用法 + 错误用法）

检查清单：
- [ ] 所有公开函数有 docstring（参数、返回值、异常、示例）
- [ ] 有 `docs/api/` 或类似 API 文档
- [ ] 错误信息包含：错误码、错误原因、建议操作
- [ ] 有 `examples/` 目录，含正常和错误用法示例

### D7：可扩展性（未来能加功能）

**达标标准：能说出"如果要加 X 功能，需要改哪里"，而且改动是局部的**

必须实现：
- 职责单一（一个类/函数只做一件事）
- 依赖注入（不硬编码依赖，方便替换和测试）
- 预留扩展点（接口已经为此准备）
- 不过度设计（不为"可能"的需求写代码）

检查清单：
- [ ] 每个类只有一个职责（SRP）
- [ ] 依赖通过构造函数注入，不硬编码
- [ ] 有接口/协议定义（Protocol 或 ABC）
- [ ] 能说出 3 个未来可能的扩展方向，以及如何局部改动

### D8：代码质量（人能读懂和维护）

**达标标准：代码审查时没有人说"这段代码看不懂"**

必须实现：
- 代码必须有中文注释（每个类、每个公开方法、每个复杂逻辑）
- 命名必须有意义（不是 temp、data、result）
- 函数必须短小（一个函数只做一件事，不超过 50 行）
- 不能有重复代码（DRY 原则）
- 旧代码修改时必须保留"修改前旧代码"注释

检查清单：
- [ ] 所有类有 class docstring
- [ ] 所有公开方法有 method docstring
- [ ] 没有超过 50 行的函数
- [ ] 没有重复代码（`radon cc` 检查）
- [ ] 修改处有"修改前旧代码"注释

### D9：真实场景验证（不只是测试通过）

**达标标准：有真实场景验证报告，知道当前模块在真实环境中的表现**

必须实现：
- 必须用真实代码库场景验证
- 验证方式：用 Agent 尝试修改真实小型 Python 项目
- 必须记录：成功场景、失败场景、边界情况、性能表现
- 必须有对比：当前实现 vs 工业级标准（如 Claude Code、Aider）的差距

检查清单：
- [ ] 有 `docs/real_world_validation/` 或类似目录
- [ ] 验证报告包含：场景描述、输入、输出、耗时、是否成功
- [ ] 有对比分析：当前实现 vs 工业级标准
- [ ] 有改进计划：下一步需要补什么

## 加固执行流程

每个模块加固时，按以下流程执行：

### Step 1：现状评估

逐一检查 9 个维度，输出：

```
模块名称：xxx
当前状态：
- D1 可观测性：⚠️ 部分达标（有日志但无 trace_id）
- D2 健壮性：⚠️ 部分达标（有校验但无重试）
- ...
差距清单：
1. 缺少 trace_id 透传
2. 缺少重试机制
3. ...
```

### Step 2：优先级排序

按以下优先级排序差距：

**P0（必须修）：安全性 > 健壮性 > 可观测性**
**P1（应该修）：性能 > 可测试性 > 接口清晰性**
**P2（可以延后）：可扩展性 > 代码质量 > 真实验证**

### Step 3：逐项加固

按优先级逐项加固，每项加固后必须有测试证明：

1. 写测试（先证明问题存在）
2. 实现修复
3. 跑测试（证明问题已解决）
4. 记录到 `docs/07_IMPLEMENTATION_LOG.md`

### Step 4：集成验证

所有维度达标后，做端到端集成测试：

1. 用 mock LLM 跑完整 Agent Loop
2. 调用所有工具，验证链路完整
3. 注入错误，验证恢复能力
4. 验证日志和统计正确

### Step 5：真实场景验证

用真实代码库场景验证：

1. 选一个小型开源项目（如 `requests` 的某个小版本）
2. 让 Agent 尝试修改（如加一个函数、修一个 bug）
3. 记录：成功/失败/边界/性能
4. 对比工业级标准

### Step 6：文档更新

更新以下文档：

- `README.md`：当前能力、运行方式、架构
- `docs/06_ARCHITECTURE_DECISIONS.md`：新 ADR
- `docs/05_LEARNING_NOTES.md`：学习笔记
- `docs/08_INTERVIEW_BANK.md`：面试题更新

### Step 7：验收签字

逐一确认 9 个维度全部达标，输出：

```
模块名称：xxx
加固完成日期：YYYY-MM-DD
9 个维度验收：
- D1 可观测性：✅ 达标（有 trace_id、日志、统计）
- D2 健壮性：✅ 达标（有校验、重试、降级）
- ...
性能基准：
- 正常场景：100ms
- 极限场景：500ms
测试覆盖率：92%
真实验证：成功修改 requests 项目
结论：可以进入下一个模块
```

## 加固产出物

每个模块加固完成后，必须产出：

1. **加固报告**：9 个维度的达标状态、具体改进内容
2. **性能基准报告**：正常场景和边界场景的耗时、内存占用
3. **真实场景验证报告**：用真实代码库验证的结果
4. **更新后的代码**：所有改进都要有测试、有注释、有文档
5. **面试题更新**：补充深度追问和边界情况分析

## 不达标不放行

如果任何一个维度未达标，必须继续加固，不能进入下一个模块。宁可进度慢一点，也不要把"半成品"带入后续开发。

## 常见问题

**Q：加固周需要多长时间？**
A：取决于模块复杂度。简单模块 3-4 天，复杂模块 5-7 天。

**Q：如果加固周结束时仍有维度未达标怎么办？**
A：继续加固，不进入新模块。可以调整后续计划，但不能降低标准。

**Q：加固时可以重构代码吗？**
A：可以，但必须有测试保护。重构后所有测试必须通过。

**Q：加固时需要新增功能吗？**
A：不新增功能。加固是"把已有功能做到极致"，不是"加新功能"。

**Q：如何判断"达标"？**
A：按本文档的检查清单逐一检查，所有清单项都打勾才算达标。
